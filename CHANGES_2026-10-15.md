# Kona Rust port - 2026-10-15 update

Copied from `D:\kona-rust-main` (all 4 copies of the port had identical source). The original is untouched.
Build: `cargo build --release` -> `target\release\kona.exe`. No new crates, no `unsafe` anywhere.

## What changed

| File | Change |
|---|---|
| `src/verbs/lanes.rs` (new) | Fast path for flat number lists. `+ - * % & | < > =` run straight over the list instead of unpacking every element into its own K atom. Lists of 65,536+ numbers are split into one chunk per CPU core with `std::thread::scope` (safe Rust). `macro_rules!` (`floats!`, `ints!`, `compares!`) generate the per-verb loops. Also `+/ */ &/ |/` in one pass, and `@[list; i; :; v]` as one copy. |
| `src/verbs/math.rs` | `eval_dyadic` tries `lanes::dyadic` first. `checked_add/sub/mul_k` shared with lanes.rs. `n _draw 0` = n random floats in [0,1) like C Kona (was a Domain error). `_setenv` no longer writes the OS environment (the last `unsafe` block); its values go to the programs Kona starts via `.envs(...)`. |
| `src/adverbs.rs` | Each-right `/:` and each-left `\:` on 9+ items used to start one OS thread per item (and clone the whole variable table for each). Now `par_apply`: one chunk per core, scoped threads borrow instead of cloning. `+/` etc. use `lanes::fold`. |
| `src/eval.rs` | Amend uses `lanes::amend_assign` for flat lists; the general amend loop no longer re-unpacks the new-values list once per index. |
| `src/main.rs`, `src/verbs/mod.rs`, `src/verbs/math.rs` | `#![deny(unsafe_code)]` -> `#![forbid(unsafe_code)]` (whole crate now forbids it). |

## Multi-threading (proof: same build, KONA_THREADS=1 vs all 12 threads, 4M numbers, ms)
`KONA_THREADS=n` sets how many threads Kona uses (1 = off). Default = every core.

| Operation | 1 thread | 12 threads | C Kona |
|---|---|---|---|
| add | 12 | 5 | 5 |
| hit test | 110 | 54 | 68 |
| `_cos` | 48 | 10 | 157 |
| `_sin` | 49 | 9 | 137 |
| `_exp` (incl. the multiply before it) | 30 | 14 | 76 |
| each-right, 20k items | 36 | 11 | - |

Cheap maths (add, compare) tops out at 2-2.5x: RAM can't feed the cores faster. Heavy maths (cos, sin) scales ~5x.
`apply_monadic_float_op` (all the `_cos _sin _exp _log ...` verbs) now uses `lanes::par_build` too.
Sums (`+/`) stay single-threaded on purpose: adding in a different order would change the last digits.

## Runs the bullet hell (D:\kona-bullet-hell) as is
`bullets.k` and the game's Python client (`kipc.py`) run on this port unchanged - press R in the game.

| Fix | Why |
|---|---|
| `src/kwire.rs` (new) + `io.rs` | `-i` now also speaks C Kona's byte format (16-byte header, `_bd` layout - read off real C Kona `_bd` output). The first 5 bytes tell it apart from the port's own format, which still works. Answers are `(0; result)` or `(1; "error")` like C Kona. |
| `main.rs` | `-i 127.0.0.1:5932` accepted (C Kona's form) as well as `-i 5932`. Still only listens on 127.0.0.1. |
| `eval.rs` amend | `@[v;i;f;x]` / `.[v;...]` with a bare name now returns the changed copy and leaves `v` alone, like C Kona (its `\.` help says so); only `` @[`v;...] `` changes `v`. Before, the bare-name form wrote back - inside a function that made a local copy of `v`, so a later `v:: ...` never reached the global. That broke the game's bullet refire. Two port tests had the old behaviour written in; they now check C Kona's. |
| `lanes.rs` | `list@ints` picks straight out of a flat list (was unpacking all of it: 128 ms -> 0 ms at 1M), `list!n` remainder (275 -> 6 ms). |

Game frame (bench.py, ms): 100k C 3.2 / Rust 7.6, 1M C 47.6 / Rust 46.9, 4M C 224 / Rust 173.

## Memory reuse + straight loops (fix 1 and fix 2)
Data first (`alloctest`, plain Rust, 1M adds, one thread): check one-or-list per element + fresh list 2.52 ms;
check once per list 2.10 ms; check once + reused list 1.36 ms; C Kona 2.35 ms.

| Change | What |
|---|---|
| `src/pool.rs` (new) + `Drop for K` (types.rs) | When the last holder of a big FloatList/IntList (65,536+) lets go, its memory goes on a shelf (max 48 lists, 1 GB) instead of back to Windows; `Arc::get_mut` only works when nobody else holds it - no unsafe. When the shelf is full the oldest list is dropped (without that, lists left from a 100k run blocked 1M reuse: 303 vs 190 ms). |
| `lanes.rs` | `fill2`: one-or-list decided once, then a straight loop per case (SIMD-friendly). `as_floats!` macro writes the 4 int/float combinations. Outputs come from the pool. `map1` for the monadic maths. Amend copies into pooled memory. |
| thread thresholds | Measured: scoped threads start fresh OS threads every operation. Heavy maths (cos/sin/exp/log) split from 64k numbers (4M cos 53 -> 7 ms on 12 threads). Cheap maths (+ - * < ...) only from 2M numbers, 512k+ per thread (a 1M 3D frame was slower on 12 threads than 1 before this). |

## Tier check: is the slowdown past ~200k the port or the language? (gravity.k unchanged, nothing else running)
ns per particle per 3D frame: C Kona 115 (100k) / 148 (200k) / 152 (500k) / 202 (1M) / 219 (4M);
this port 65 / 88 / 110 / 115 / 133. Both curves rise the same way once the frame's lists outgrow the CPU cache
(Ryzen 5 3600: 16 MB L3 per half of the chip; ~15 live lists x 8 bytes x 200k = 24 MB). K runs one full pass over
memory per operation, so out of cache every pass runs at RAM speed. That is the array-language model + hardware,
not a port fault. Tried in the port, measured, no gain: cheap-maths threads from 128k/256k (spawn overhead, RAM is
the limit), pool 4 GB instead of 1 GB. Defaults kept. New knobs to re-measure on other machines without rebuilding:
`KONA_CHEAP_MIN`, `KONA_CHEAP_CHUNK` (numbers), `KONA_POOL_MB`.
The fix for this is fusion (run chains of element-wise maths in cache-sized blocks, no in-between lists) - not done.

## GPU Kona (`--features gpu`, wgpu 30.0.1 + pollster + bytemuck)
`cargo build --release --features gpu` builds the GPU in (kona.exe 1.2 MB -> 8.3 MB, one file, nothing for the
player to install beyond the graphics driver). Plain `cargo build --release` = CPU-only Kona; the GPU verbs then
answer "feature disabled". Still zero `unsafe` in our code (wgpu keeps the driver calls inside itself).
Backups of the build files before this: `Cargo.toml.before-gpu`, `Cargo.lock.before-gpu`.

| K verb | What |
|---|---|
| `h: _gup list` / `_gup (h; list)` | float list -> 32-bit floats on the card (int list -> 32-bit ints); refill in place |
| `_gdown h` | copy back -> float / int list |
| `k: _gk "file.wgsl"` | compile a WGSL compute kernel (entry `main`, `@workgroup_size(256)`), cached by source |
| `_grun (k; handles; params; n)` | buffers at @binding(0..), float params next, n threads; index = gid.x + gid.y*16776960u |
| `_gfree h` | drop a buffer |

Bad kernels / missing buffers / wrong binding counts come back as Kona errors (wgpu validation error scopes),
tested: Kona keeps running. Test kernel `gpu_tests/add.wgsl`: 1M (a+b)*2 on the GPU = CPU answer exactly.
Plain-Rust check first: 4M adds 0.2 ms on the RTX 3090 (Vulkan), 3.5 ms with copy-back, 0 of 4M wrong.

Used by `D:\kona-gravity-3d\gravity_gpu.k` + `gravity.wgsl` (key G in the game): 1M particles GPU frame 0.45 ms,
whole frame with packed positions 2.5 ms in Kona; through the server to the page ~16 ms = ~62 frames/s at 1M
(CPU Rust Kona: ~150 ms). 16M particles run (~3 frames/s, limited by moving 64 MB per frame to the page).

## The `_sys` door - Kona Rust talking to C++ (Made by Claude, 2026-10-15)

One door out of Kona, Martin Richards' BCPL `sys(Sys_gl, fno, args)` way: `_sys (library; function; args)`.
Kona only reaches what is compiled in behind the door; it never loads outside code by itself.

- library 1 = GPU (0 up, 1 down, 2 kernel, 3 run, 4 free - same arguments as `_gup` ... which still work)
- library 2 = C++ game library built into kona.exe (cxx bridge, `--features cpp`)
- library 3 = the same C++ library running next door as `cpp/kgame_server.exe` (127.0.0.1:5990, or KONA_DOOR3)
- C++ functions (cpp/kgame_core.h): 0 echo, 1 sum, 2 move (pos;vel;dt), 3 world n, 4 step (h;dt), 5 read h, 6 free h

Files: src/door.rs, src/door_net.rs (no unsafe), src/door_cpp.rs (the cxx bridge - the ONLY module allowed
unsafe, and only with `--features cpp`; plain builds still `forbid(unsafe_code)` for the whole crate), build.rs,
cpp/ (kgame_core, kgame_cxx, kgame_server, door_test.k, door_race.k). Backups: *.before-cpp.
Build: `cargo build --release --features "gpu cpp"` (also builds cpp/kgame_server.exe with the same MSVC compiler).
Checks: door_test.k - both C++ libraries match K's own maths exactly, worlds identical, errors come back as
Kona errors, GPU works through the door. Plain build: 61/61 tests.

Race (door_race.k, per call, two runs agreed):
| | K itself | door 2 (built in) | door 3 (next door) |
|---|---|---|---|
| tiny call | 0.15 us | 1.2 us | 40 us |
| move 1k floats | 1.6 us | 4.6 us | 58 us |
| move 100k | 0.05 ms | 0.45 ms | 1.8 ms |
| move 1M | 1.9 ms | 8.3 ms | 24 ms |
| move 4M | 8.4 ms | 33 ms | 100 ms |
| 1M world step, data stays in C++ | - | 2.8 ms | 2.8 ms |
| read 1M positions back | - | 9.4 ms | 22 ms |
Door 2's cost on big lists is copying (two lists in, one out); door 3 adds the trip through the socket.
When the data stays on the C++ side and Kona only sends commands, both doors are equally fast.

## Library 4 = Martin's BCPL, library 0 = run door calls at the same time (Made by Claude, 2026-10-15)

- `_sys(4;0;"cmd")` runs a command in Martin Richards' own BCPL system (his cintsys, built for Windows in
  D:\kona-bcpl - see its README) and returns the numbers it printed; `_sys(4;1;"cmd")` returns the text.
  cintsys programs are kept running as workers (one per core at most) and fed commands through a pipe.
  src/door_bcpl.rs, no unsafe. Settings: KONA_BCPL (cintsys path), KONA_BCPL_WORKERS.
- `_sys(0;0;calls)` runs a list of (lib;fn;args) door calls on separate threads, one per core at a time,
  results in order. Works for any library (BCPL and C++ mixed in one call tested). Library 3 calls still take
  turns on its one connection; GPU calls take turns on the card.
- cpp/bcpl_race.k: 12 x kqueens 13 one at a time 5.1 s, all at once 1.1 s (4.4x on 6 cores / 12 threads);
  sizes 10..14 at once = the time of size 14 alone. Plain build 61/61 tests.
